OSIRIS LANGUAGE GUIDE
=====================

WELCOME.

This is the plain text guide to the Osiris language.
It is meant to be read like an old README dropped in a release folder.

No fluff. No ceremony. Just the language, the shape of programs, and the way
to write them so they stay readable later.

---------------------------------------------------------------------------
WHAT OSIRIS IS
---------------------------------------------------------------------------

Osiris is a small deterministic language for turning inputs into outputs.
It is good for:

  * text transforms
  * byte work
  * bitwise work
  * data pipelines
  * repeatable scripts
  * language/tooling experiments

The main idea is simple:

  input -> named transforms -> output

---------------------------------------------------------------------------
PROGRAM FILES
---------------------------------------------------------------------------

Osiris source normally lives in `.osr` files.

A program is a list of statements.
Statements can be separated by newlines or semicolons.

Comments:

  // line comment
  # line comment

---------------------------------------------------------------------------
THE SHAPE OF A PROGRAM
---------------------------------------------------------------------------

The usual order is:

  1. package
  2. export
  3. import
  4. macro
  5. let
  6. emit

That is not a law.
It is just the shape that reads best.

Example:

  package sigil 1.0.0
  export visible

  import "std/text" as text

  let seed = "osiris::demo"
  let visible = text.slug(seed)
  emit visible

If a file is meant to be imported, give it a package name and explicit exports.

---------------------------------------------------------------------------
STATEMENTS
---------------------------------------------------------------------------

PACKAGE

  package name
  package name 1.2.3

Declares the module identity.
The version is metadata and can be used by import selectors.

EXPORT

  export name
  export alpha, beta, gamma

Exports only the listed names.

IMPORT

  import "./local.osr" as local
  import "./local.osr@2.1.0" as local
  import "std/text" as text
  import "std/text@1" as text

Imports are always aliased.

LET

  let name = expression
  let count u32 = 3
  let callback func(u32) string = render

Bindings are lexical and lazy.
An annotation checks a value; it does not cast.
Prefer clear names.

MACRO

  macro name(arg, other) => expression

Macros expand before evaluation.
Use them for syntax shaping, not for hiding business logic.

FUNC

  func name(arg, other) => expression

  func scale(value u32, factor u32) u32 {
    let tmp u32 = value + factor
    return tmp * u32(2)
  }

Functions are lexical and can recurse.
Types follow names without a colon.
Unannotated parameters and results remain dynamic.
Typed calls and all result paths are checked before execution.
Use them when a transform deserves a name.

RETURN

  return expression
  return

Return exits the current function or loop body immediately.

IF, AND, OR

  emit if(test, left, right)
  emit and(left, right)
  emit or(left, right)

These are special forms.
Use them for short conditional logic.

WHILE

  while keep_going {
    let next = step
  }

Use while for open-ended repetition.

FOR

  for item in items {
    emit item
  }

Use for when you want to walk a list or other sequence.

BREAK / CONTINUE

  break
  continue

Break exits the nearest loop.
Continue skips to the next iteration.

TRY / CATCH

  try { risky() } catch err { fallback(err) }

Use this when a computation might fail and you want to handle the failure
inline. The catch binding receives an error value.

ERROR MODEL

Osiris uses structured error records instead of bare strings.

  error(kind, message)
  wrap(cause, kind, message)
  cause(err)
  unwrap(err)
  withmeta(err, key, value)
  withdebug(err, key, value)
  errmeta(err)
  redact(err)

The base error record is immutable. When you attach more information, Osiris
returns a new error record instead of mutating the old one.

The public error shape includes:

  * kind/code
  * message
  * optional cause
  * optional source location
  * optional stack trace
  * optional operation, resource, retryability, severity, and user message
  * optional correlation id, component, remediation, and timestamp
  * optional public metadata
  * optional debug-only metadata

The standard taxonomy stays deliberately small:

  InvalidArgument
  NotFound
  AlreadyExists
  PermissionDenied
  Unauthenticated
  Unavailable
  Timeout
  Cancelled
  Conflict
  ResourceExhausted
  OutOfMemory
  OutOfRange
  Unsupported
  NotImplemented
  ParseError
  TypeError
  EncodingError
  IOError
  NetworkError
  DatabaseError
  InternalError
  UnknownError

Domain-specific libraries may define their own kinds when they need more
specific error classification. The rule is to keep the public kind stable and
machine-readable, not to encode policy in a free-form string.

Use the public members when you want to inspect an error in code:

  emit err.kind
  emit err.code
  emit err.message
  emit err.cause
  emit err.source
  emit err.location
  emit err.stack
  emit err.metadata
  emit err.debug
  emit err.redacted

The public metadata view is stable enough for logs and APIs.
The debug metadata view is intentionally separate so sensitive data does not
leak into normal output.

Errors are comparable by structure, serializable through `encode` / `decode`,
and safe to move across task boundaries because they are cloned and normalized
at runtime boundaries.

Native and host errors are normalized into Osiris error records before they
leave the runtime. The source name is preserved when one is available.

Error checking and propagation use a short, explicit surface:

  ?               propagate the current failure to the function boundary
  try { ... }     evaluate a recoverable block
  catch name { }  bind the failure and handle it
  matches(err, k) test an error kind or code without parsing text
  is(err, k)      alias for matches

The rule is simple: ordinary failure stays recoverable and visible, while the
happy path stays short and readable.

RESULT AND OPTION VALUES

Osiris also has standard result and option helpers for code that wants a more
explicit success and absence model.

  ok(value)
  err(error)
  some(value)
  none()
  isok(value)
  iserr(value)
  issome(value)
  isnone(value)
  unwrap(value)
  expect(value, message)
  or_else(value, fallback)

Use Result when a computation can fail but you still want to carry a value.
Use Option when a value may or may not exist without that absence being a
failure.

The postfix `?` operator is the short propagation form. It evaluates the
expression and, if it produces a recoverable failure, returns that failure to
the current function boundary immediately. That keeps the happy path short
without hiding the possibility of failure.

PANICS, TRAPS, AND FATAL ERRORS

  panic(message)
  trap(message)
  assert(condition, message)

These are for unrecoverable states and internal invariants. They raise a
fatal structured error and bypass ordinary try/catch handling. Osiris treats
recoverable failures as structured values, but fatal faults as process-level
stop conditions.

`defer { ... }` is the language's lexical cleanup construct. It registers a
block at the point of execution and runs it once at scope exit in LIFO order,
including normal fallthrough, return, loop exits, failure, cancellation, and
task termination. It is deterministic scope cleanup, not a destructor or
garbage-collector finalizer. Fatal faults are not recoverable across normal
function boundaries, task boundaries, or native boundaries.

Use errors for expected failure, Option for absence, Result for explicit
fallibility, and panic/trap/assert for impossible states.

CONTEXT AND WRAPPING

  wrap(cause, kind, message)
  cause(error)
  unwrap(error)
  withmeta(error, key, value)
  withdebug(error, key, value)
  errmeta(error)
  redact(error)

Wrap preserves the original cause chain and adds domain context. Use it when
you want to annotate a failure with operation names, resource names, retry
state, or user-facing explanations without losing the original root cause.

EMIT

  emit expression
  emit left, right

Evaluates its expression once, appends one value to the ordered program output,
and continues with the next statement. It is valid at the top level and in
synchronously executed blocks, including loops, functions, call-shaped
`if` branches, `match`/`switch` arms, and `try`/`catch` bodies. It is not a
block result and does not replace `return`.

Multiple expressions are concatenated into one output value with `, ` using
the same text path as `cat(...)`. Output committed before a later error or
cancellation remains visible.

Module initialization cannot emit. A synchronously called exported function
may emit into its caller's output sequence. Concurrent bodies (`spawn`,
`parallel`, `race`, `select`, and `timeout`) must return a value instead; emit
that value in the caller after `await` where applicable.

BLOCKS

  emit {
    let x = 2
    let y = 3
    x + y
  }

Blocks create local scope and return the last expression.
Blocks may also contain local function declarations and loops.

---------------------------------------------------------------------------
EXPRESSIONS
---------------------------------------------------------------------------

Osiris expressions are compact and composable.

You can use:

  * arithmetic: + - * / %
  * comparisons: == != < <= > >=
  * boolean logic: && || !
  * bitwise ops: & | ^ ~ << >>
  * calls: foo(x, y)
  * member access: text.slug(...)
  * lists: [1, 2, 3]
  * blocks: { let x = 1; x + 2 }
 * match expressions:

      emit match [1, 2] {
        [a, b] => a + b;
        _ => 0
      }

  * switch expressions:

      emit switch [1, 2] {
        [a, b] => a + b;
        _ => 0
      }

  * control flow:

      func fact(n) => if(n == 0, 1, n * fact(n - 1))
      while ready { break }
      for x in xs { continue }
      try { uint("7") } catch err { fallback(err) }

Numbers may be plain, hex, binary, or sized fixed-width values such as:

  42
  0xff
  0b1010
  42u
  1.5f32
  2.25f64
  42i16
  255b
  1u8
  2u16
  3u64

Use `uint(...)` when you want the host-width unsigned form explicitly.
Use `f32(...)` or `f64(...)` when you want explicit float widths.
Use `u8(...)`, `u16(...)`, `u32(...)`, `u64(...)`, `u128(...)`, `u256(...)`,
`u512(...)`, or `u1024(...)` when you want exact unsigned fixed-width math.
Use `i8(...)`, `i16(...)`, `i32(...)`, `i64(...)`, `i128(...)`, `i256(...)`,
`i512(...)`, or `i1024(...)` when you want signed fixed-width integers.
Use `byte(...)` when you want to say "raw 8-bit data" directly.

Exact decimal values may use a `d` suffix or the `dec(...)` builtin:

  0.1d
  1.25d
  dec("0.3")

Complex values may use an `i` suffix or the `complex(...)` builtin:

  5 + 3i
  complex(5, 3)
  abs(3 + 4i)

If you need bytes, use the byte helpers and fixed-width casts.

Tensor values are contiguous on the inside.

  tensor([[1, 2], [3, 4]])
  matrix(2, 2, [1, 2, 3, 4])
  shape(value)
  flatten(value)
  transpose(matrix)
  dot(a, b)
  matmul(left, right)
  reshape(value, [rows, cols])
  view(tensor)
  clone(tensor)

The shape metadata stays separate from the flat data buffer.
That is the point. Keep the data linear and the dimensions explicit.
Tensor arithmetic is vectorized when possible, so simple element-wise math is
lowered to parallel chunk work instead of a naive scalar loop.
Compatible shapes broadcast across axes the way NumPy does.
Obvious constant shape mistakes are caught during assembly before runtime.

Math helpers live in the same direct style.

  sin(x)
  cos(x)
  tan(x)
  asin(x)
  acos(x)
  atan(x)
  exp(x)
  log(x)
  log(x, base)
  log10(x)
  log2(x)
  hypot(a, b, ...)
  norm(v)
  vector(...)
  vec(...)

Use these for scalar math and linear algebra without writing custom loops
every time.

There is also a GPU compiler target.

  osiris gpu file.osr

This emits kernel source and a kernel plan for tensor math and matrix
operations. Use it when you want to inspect how a program would be lowered for
a GPU backend.

Strings are their own primitive too.

  "osiris"
  len("osiris")
  at("osiris", 2)
  setat("osiris", 0, "O")

Do not rely on strings as hidden numbers.
If you want bytes, use byte helpers.
If you want numbers, use numeric literals or explicit casts.

Physical units are first-class values.

  Meter
  Second
  Kilogram
  meter
  second
  kilogram
  m, s, kg, A, K, mol, cd
  Newton, Joule, Watt, Pascal, Coulomb, Volt, Farad
  Ohm, Siemens, Weber, Tesla, Henry, Lumen, Lux
  Becquerel, Gray, Sievert, Katal, Liter, Minute, Hour, Day, Week
  kilo, mega, giga, tera, milli, micro, nano, pico
  Pi, Tau, E, SpeedOfLight, Planck, Boltzmann, Avogadro
  10 * Meter / (2 * Second)
  2 * kilo * Meter
  30 * minute
  2 * Pi
  (3 * Meter) + (2 * Meter)

These names are just identifiers.
That means you can multiply, divide, store, and pass them around like any
other value.

Use matching dimensions for addition and subtraction.
Multiply and divide to build derived units.

Arbitrary-precision values are available when plain machine numbers are not
enough.

  bigint("9223372036854775808")
  bigfloat("1.5")

Use these for very large integer or floating-point calculations that should not
overflow the normal fast path.

---------------------------------------------------------------------------
HOW TO WRITE PROGRAMS
---------------------------------------------------------------------------

Write Osiris like a pipeline.

Good habits:

  * keep the package and exports at the top
  * use imports instead of copying helpers into every file
  * name intermediate values
  * keep macros small and obvious
  * use functions for repeated logic and recursion
  * use loops when the shape is iterative
  * use match for shape-driven branching
  * use switch when you want the same matcher with a more table-like feel
  * keep emit at the end when possible
  * prefer deterministic transforms
  * keep the module surface narrow

Good Osiris code is easy to trace.
If a program is hard to inspect, it is usually written in the wrong shape.

---------------------------------------------------------------------------
BYTE AND BIT WORK
---------------------------------------------------------------------------

Osiris has a strong byte and bit surface.

Useful builtins:

  * u8, u16, u32, u64, u128, u256, u512, u1024
  * band, bor, bxor, bnot
  * shl, shr, rotl, rotr
  * hex, bin, bytes
  * pack, unpack
  * encode, decode

Use these for:

  * hashes
  * compact identifiers
  * binary formats
  * content-addressed work
  * low-level transforms

---------------------------------------------------------------------------
DATA WORK
---------------------------------------------------------------------------

Useful builtins:

  * read, readbytes, write
  * lines
  * csv
  * jsonparse
  * hash, mix, slug, join, split, chunks

This makes Osiris good for:

  * build steps
  * file transforms
  * batch cleanup
  * repeatable output generation
  * data shaping

---------------------------------------------------------------------------
MODULES
---------------------------------------------------------------------------

File modules can be versioned and imported explicitly.

Example:

  package local 2.1.0
  export visible

  let visible = ...

Use package/version headers when a file is meant to be reused.
Use export to keep the public surface small.

---------------------------------------------------------------------------
EXAMPLE
---------------------------------------------------------------------------

  package sigil 1.0.0
  export visible

  import "std/text" as text

  let seed = "osiris::demo"
  let basis = hash(seed)
  let salt = mix(basis, "scarab", "moon")
  let visible = text.slug(join("-", chunks(mix(basis, salt), 4)))
  emit visible

This is the preferred style:

  * explicit package
  * narrow export surface
  * imported helpers
  * named steps
  * one clear final output

---------------------------------------------------------------------------
FINAL NOTE
---------------------------------------------------------------------------

Osiris is meant to stay small, sharp, and inspectable.

Write it like something you will read again later.
Keep the data flow obvious.
Keep the modules tight.
Keep the outputs deterministic.

That is the Osiris way.
